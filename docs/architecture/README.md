# Архитектурный каркас

С 2026-10-01 есть [реализованный локальный MVP 0.3](lokalnyy-mvp.md). Он использует Python/SQLite и браузер; постоянные интеграции и окончательный производственный стек открыты.

## Исходная проектная рамка

Предлагаемый поток: веб-интерфейс → сервер → фоновое исследование → сохранённые результаты → модерация в веб-интерфейсе.

Функциональная декомпозиция областей и аналитического контура: [Карта модулей](module-map.md). Это проектное предложение, не разбиение на сервисы или готовый план реализации.

Методология актуализации источников и варианты поставщиков описаны в [модуле онлайн-ресерча](../../research/modul-onlayn-resercha-i-aktualizacii-dannykh.md); ни один сервис не выбран.

По заданию 2026-09-30 создан отдельный [исследовательский прототип поиска](../../research/poisk-i-podbor/README.md). Он проверяет план, контракты и первичный отбор; Exa использован в текущей сессии как подключённый инструмент исследования. Это не постоянная интеграция приложения и не решение о его стеке.

- apps/web: формы, загрузки, просмотр статусов, сравнение и модерация.
- apps/api: операции с брифами, заданиями, кандидатами и решениями; управление доступом после определения ролей.
- services/research-worker: планирование и выполнение длительных этапов исследования с контролем затрат и сохранением прогресса.
- packages/domain: общие определения сущностей и статусов.
- packages/connectors: получение данных и сведения об их происхождении.
- packages/scoring: версионируемые расчёты и модели.

Потребуются хранение структурированных данных и файлов, механизм фоновых заданий, история версий оценок и учёт затрат. Конкретные базы, очереди, фреймворки и поставщики пока не выбраны.

Следующий архитектурный документ должен определить границы MVP, жизненный цикл задания, обработку ошибок и повторов, отмену, обновление данных, ограничения расходов и модель доступа.
